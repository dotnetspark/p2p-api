# Data Model: Invoice Approval and Payment

## Overview

This feature models the accounting and settlement steps that occur after invoice
matching. A matched invoice may be approved exactly once per logical request,
producing two balanced GL entries, and may then be marked paid, which closes the
linked purchase order.

## Entities

### Invoice

**Purpose**: Represents the payable obligation as it progresses from matched to
approved to paid.

**Fields**:

- `id`: Stable invoice identifier
- `vendor_id`: Foreign key to `Vendor.id`
- `purchase_order_id`: Foreign key to `PurchaseOrder.id`
- `invoice_number`: Vendor-provided invoice reference
- `invoice_amount`: Monetary amount of the invoice
- `status`: One of `PENDING`, `MATCHED`, `APPROVED`, or `PAID`
- `last_match_outcome`: Most recent 3-way match result from the earlier feature
- `approved_at`: Optional timestamp when approval succeeded
- `paid_at`: Optional timestamp when payment succeeded

**Validation rules**:

- Approval is allowed only when `status = MATCHED`
- Payment is allowed only when `status = APPROVED`
- Approval transitions `MATCHED -> APPROVED`
- Payment transitions `APPROVED -> PAID`
- Rejected approval or payment attempts must leave status unchanged
- The current repository assumption of one invoice per purchase order remains in force
  for this feature slice

### GLEntry

**Purpose**: Captures one accounting record generated by invoice approval.

**Fields**:

- `id`: Stable GL entry identifier
- `invoice_id`: Foreign key to `Invoice.id`
- `account_code`: Accounting account used for the entry
- `debit`: Debit amount, zero when the entry is the credit side
- `credit`: Credit amount, zero when the entry is the debit side
- `posted_at`: Timestamp when the entry was created

**Validation rules**:

- Exactly two `GLEntry` rows are created for each successful approval
- The two entries must balance to the invoice amount
- One entry must credit `AP_CONTROL`
- One entry must debit the vendor-category-derived expense account or the
  unclassified fallback account
- No additional GL entries are created when the approval request is replayed with the
  same idempotency key

### Vendor Expense Account Rule

**Purpose**: Determines the expense account code to use for an approved invoice based
on vendor classification.

**Fields**:

- `vendor_category`: Vendor category or type used as the lookup key
- `expense_account_code`: Expense account to use for that category
- `fallback_account_code`: Catch-all account used when the category is missing or
  unmapped

**Validation rules**:

- Lookup must always yield an account code, either specific or fallback
- Missing or unmapped vendor categories must not fail approval
- Mapping decisions must be deterministic for the same vendor category input

### Invoice Approval Result

**Purpose**: Machine-readable result describing a successful or rejected approval
attempt.

**Fields**:

- `invoice_id`
- `invoice_status`
- `generated_gl_entry_ids`: Exactly two identifiers on success
- `payable_account_code`
- `expense_account_code`
- `approved_at`
- `next_action`

### Invoice Payment Result

**Purpose**: Machine-readable result describing a successful or rejected payment
attempt.

**Fields**:

- `invoice_id`
- `invoice_status`
- `purchase_order_id`
- `purchase_order_status`
- `paid_at`
- `next_action`

## Relationships

- `Vendor 1 -> many Invoice`
- `PurchaseOrder 1 -> zero or one Invoice` within the current repository scope
- `Invoice 1 -> many GLEntry`
- `Vendor Expense Account Rule` is derived from vendor master data and a static
  category-to-account mapping

## Business Invariants

- An unmatched invoice must never be approved
- An unapproved invoice must never be marked paid
- A successful approval always creates exactly two balancing GL entries
- Expense account classification must fall back safely rather than fail on missing
  vendor category context
- A successful payment closes the linked purchase order in this feature slice
- Idempotent replay must preserve the original logical outcome for approval and
  payment requests

## State Transitions

### Invoice

- `MATCHED -> APPROVED`: valid when approval succeeds and two balanced GL entries are
  posted
- `APPROVED -> PAID`: valid when payment succeeds
- `MATCHED -> MATCHED`: valid when approval is rejected
- `APPROVED -> APPROVED`: valid when payment is rejected

### PurchaseOrder

- `RECEIVED -> CLOSED`: valid when the linked approved invoice is marked paid
- `CLOSED -> CLOSED`: valid on idempotent replay of a successful payment request
